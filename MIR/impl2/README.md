# MIR-1 validator, second implementation

A conformance validator for MIR-1, written in Go from `../MIR-1-spec.md`. It
exists to test the specification rather than the reference implementation.

```
go build -o mir-validate .
./mir-validate ../records/MIR-R1.json --verify-remote
go test ./...
```

Go 1.27 or later. Standard library only; `go.mod` names no dependencies. The
tests compare this implementation against tables cut from the reference's
Unicode data, and an older runtime folds different code points.

## Why a second implementation

A format with one implementation is a project. The claim MIR-1 makes about
itself is stronger than that: section 7.1 says the suite can be implemented from
the document alone, by someone with no access to the authors, within one working
day. That claim is checkable only by implementing it, and it fails in a way that
reading cannot detect.

This implementation was written from the text and shares no code with
`../validate.py`. It reproduces every check, the canonical form of section 4.13,
the locator protocol of section 4.12, the subprocess behavior of C-04, and the
report shape of section 7.4, because a difference in the report would hide a
difference in the verdict.

## What it found

The reference implementation did not implement its own canonical form. It
serialized records with a general-purpose JSON encoder, which writes exponent
notation for values at or above 10^16 and below 10^-4, while the specification
allows a conforming record to write those values without an exponent. Two
serializers that spell one value differently produce two ids for one record, and
the id is the content address.

The fix is in both implementations and the id of the worked example did not
change, because none of its numbers is affected. See `../records/NOTES.md`,
D-5. This is the class of defect the exercise is for: not a difference of style,
but a rule that could not be implemented twice as written.

## How agreement is checked

`../crosscheck.py` builds this binary, runs both validators with `--json` on
every record and example in the repository, on seventeen mutations of the worked
example and three of the conforming fixture, and on a corpus of random documents,
and diffs the reports byte for byte. It exits non-zero on a single byte of
disagreement.

```
python3 ../crosscheck.py --fuzz 400
```

Half the random documents are arbitrary JSON shapes, which exercise the canonical
form; half are mutations of a conforming record, which reach the branches an
arbitrary shape cannot. The run ends with a coverage table naming, per check, how
many documents passed it, how many failed it, and how many distinct messages it
produced. Agreement on a corpus that yields one message per check is agreement
about nothing, and the table is what shows the corpus was not that.

The canonical-form vectors in `testdata/canonical_vectors.json` are generated by
the reference implementation and asserted by `canonical_test.go`. They are the
part of the agreement that a record-level test can miss: two implementations can
agree on every record in a repository whose numbers are all small.

## Input that is not JSON

Both implementations reject the same malformed input with the same detail: `NaN`
and `Infinity`, which are not JSON; a lone surrogate escape (`\ud800`), which the
canonical form cannot represent; bytes that are not valid UTF-8; and a document
nested more than 256 levels deep (section 4.13). An earlier version of this file
listed two of these as deliberate differences. They are not differences now, and
`../crosscheck.py` fails if either becomes one.

## Text handling

`str.strip()`, `str.casefold()`, `str.lower()` and `repr()` are not Go's `strings`
functions, and the differences reach reports: C-04 quotes the falsifier's
lowercased output, C-07 quotes the host's lowercased etag, and C-10 compares
operators and funding sources after trimming and folding. Go also ships a newer
Unicode table than the reference implementation runs on, so it folds case pairs
and prints code points that Python does not.

`reference.go`, `casefold.go` and `printability.go` pin these operations to the
reference Unicode version, 16.0.0, using tables generated from Python and held as
data in `unicode_tables.go`. The tests check every code point, so an upgrade on
either side is a test failure rather than a silent divergence. Regenerate with
the `testdata/make_*.py` scripts after either.

## Reading order

`canonical.go` first. The id of a record is the one thing every other check
depends on, and it is the one place where two correct-looking programs diverge.
`checks.go` follows the numbering of the specification. `store.go` holds the
locator protocol. `pyformat.go` and the three files under Text handling hold the
report's spelling of values. `main.go` is the command line and the report.
